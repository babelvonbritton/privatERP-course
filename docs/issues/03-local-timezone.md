# Issue 3: Dates from timestamps use UTC

- Category: `bug`
- State: `ready-for-agent`
- Severity: should fix (Ponytail audit v1.0.6, finding 3)

> *This was generated by AI during triage.*

## Problem

Dates derived from timestamps use UTC, so an invoice created 26 November 2026
at 02:30 WIB prints an issue date of 25 November on the invoice document. A
payment recorded before 07:00 local shows the previous day in the payment
list, and a pay run marked paid before 07:00 shows a paid date one day early
in the table and on the paycheck.

## Fix (decided design, overrides the audit's suggested fix)

Add a dedicated "Local timezone" section in Settings where the user picks
where they live (IANA timezone picker). No location detection of any kind:
no GPS, no IP geolocation, never. Default the setting to the device timezone
so it starts correct; the user can change it anytime. All date derivations
(invoice and paycheck dates, payment dates, today's date, the invoice-number
day prefix, dashboard dates) use the chosen zone. Stored timestamps stay raw
millisecond instants. No NTP and no network time of any kind: the bug is date
conversion, not clock accuracy (see ADR 0002). The picker works at 390px and
follows the app's existing themed-picker patterns. Bilingual English and
Indonesian.

## Acceptance

- A 02:30 WIB timestamp renders 26 Nov under Asia/Jakarta and 25 Nov under UTC.
- Changing the setting changes displayed dates everywhere.
- The default equals the device timezone.
- All existing tests still pass.
